小白的说明

Metadata-only deployment research; no inference, measured RAM/VRAM or model capability benchmark.

研究口径（2026-11-26）：本文完成公开模型资产的只读核验、原始配置推导和 12 项独立轻量检查，并核对第三方实际运行报告。未下载权重、未运行 Bonsai 2.5 推理，因而不提供本站生成速度、峰值内存或任务正确率实测。本文是部署决策研究，不是模型性能测评。

结论先行： PrismML 在 11 月 24 日发布 Ternary Bonsai 2.5 27B，目标是让高参数量模型在受限内存设备上执行多轮工具任务。5.93 GB 是厂商报告的紧凑模型口径；实际最小 GGUF 文件是 5,993,834,848 字节（约 5.99 GB / 5.58 GiB）。标准 llama.cpp 的 Q2_0 资产则约 7.67 GB。即使文件能装进设备，推理还要给上下文、运行时、线性注意力状态、视觉模块和操作系统留空间。因此，先选正确权重格式和运行时，再根据任务的上下文预算决定机器，不能用 5.9 GB 当作整机内存门槛。更紧凑的权重也为本地 AI、私有化部署与数据自主可控提供了新的选型空间，但隐私与数据安全仍须通过存储、网络、工具权限及真实任务验收来保障。

1. 为什么这次不是简单的“更小模型”

与上一代 Bonsai 2 27B 相比，新版仍以 Qwen3.8-27B 的混合注意力架构为基础。真正值得研究的是长任务执行：模型能否在读取工具结果后修正计划，而不是靠一次漂亮回答掩盖后续失败。厂商保留三值权重表示，同时针对 Agent 编程与工具任务改善行为。

厂商报告的三值组量化允许权重使用 -1、0、+1，每组 128 个权重共享一个 FP16 缩放因子。对块进行 Hadamard 变换后量化，推理端也要完成与该表示匹配的激活变换。这解释了为什么文件扩展名同为 GGUF，不代表旧版 llama.cpp 一定能正确执行。参见官方模型卡和发布说明。

从信息量看，单个三值符号的理论编码容量是 log₂3，约 1.585 bit。五个三值符号共有 243 种组合，可放进一个字节。按 128 个符号、26 字节整数打包及 2 字节缩放值的简化示例，组平均为 1.75 bit/weight。若改用每个符号 2 bit 的槽位，组平均为 2.125 bit/weight。真实模型还包括其他精度张量、容器结构、对齐等开销；不能拿教学公式直接宣布实际模型每个参数都是 1.75 bit。

本站用 Python 标准库穷举了 243 种五符号组合，检查编码唯一性与往返恢复。这是编码原理实验，不是实际 PTQ1_0 内核的复现，也不证明三值量化后模型质量等于 FP16。它的作用是把压缩机制和模型能力评估明确分开。

图1：三值权重表示与分组缩放示意。矩阵是教学示例，不代表实际模型权重或稀疏率；实际 Bonsai 量化还涉及 Hadamard 变换，按官方模型卡每 128 个权重共享一个 FP16 缩放因子。编码及打包取决于具体格式，约 6 GB 指已核验 PTQ1_0 文件大小，不是运行内存。

可选视觉投影文件 Q8_0 为 629,246,976 字节，BF16 为 931,145,856 字节。仅文本推理不应把两个投影文件一并下载。MTP 变体包含推测解码所需额外头，通常应选择一个普通或 MTP 文件，而不是整仓下载。该 GGUF 仓库的八个文件合计约 44 GB；实际部署只需合适的一种权重和按需选择的视觉资源。模型下载应从官方固定 revision 的 GGUF 文件列表选择所需文件，再根据下一节内存预算和运行时兼容性确定是否下载，不必克隆全仓。

同样需要区分 GB 和 GiB：1 GB 是 10⁹ 字节，1 GiB 是 2³⁰ 字节。系统监测工具可能用不同单位呈现，采购或部署不能直接把它们混为一谈。

3. 6GB 内存为什么不是答案：上下文缓存的独立计算

本次读取 Qwen3.8-27B 基础配置，记录 64 层、每四层一次完整注意力、4 个 KV heads、head_dim 256、最大位置数 262144。配置层类型中有 16 层完整注意力，其余为线性注意力。以基础架构不变、单序列、完整注意力 K 和 V 均 FP16、不做 KV 量化或额外对齐为假设：

KV_bytes_per_token = 2 × 16 × 4 × 256 × 2
                   = 65,536 bytes

4,0960.25 GiB
8,1920.50 GiB
32,7682.00 GiB
131,0728.00 GiB
262,14416.00 GiB

这是本站根据公开配置计算的理论缓存载荷，不是实际 RAM/VRAM 读数。真实 Bonsai 导出与加载器配置仍需核实。它不计线性注意力递归状态、激活、工作区、视觉、并发、框架分配和系统开销；KV 量化、滑动策略、统一缓存及 CPU/GPU offload 均可改变实际分配。文件映射也不等于每个文件字节在所有时刻都驻留内存。

例如完整 PTQ1_0 文件约 5.58 GiB，加 32K 上下文的理论完整注意力 KV 约 2 GiB，得到约 7.58 GiB 的简化预算项之和。它已经接近 8 GiB，而其余开销尚未计算。因此不能保证 8GB 设备稳定执行 32K Agent 工作负载。262K 是架构允许的上限，而非设备能免费提供的上下文。

图2：运行时内存组成的简化示意。约 6 GB 是 PTQ1_0 权重文件的十进制大小，并非实际常驻内存。还需计入线性注意力状态、激活、视觉模块（按需）、操作系统及并发等；正文 KV 表是单序列、FP16、完整注意力部分的理论计算，不是实测峰值。

新版 MLX 模型卡当前说明包含语言权重、FP16 视觉塔和可选 MTP。此前 Bonsai-demo 文档的 2.5 MLX 描述仍有文本专用口径，存在更新时差。部署前应记录模型 revision、加载器版本和具体输入能力，不以旧 README 覆盖新资产说明；本文未验证 MLX 实际图像推理。

单用户低显存服务先确认 --parallel 1（短参数 -np 1）、短上下文、正确采样和当前运行时支持。建议从 4K 或 8K 开始做设备验证，再扩大上下文；此为测试起点，而非已验证的硬件最低配置。厂商提醒默认 xhigh 推理时过小输出 token 限制可能在思考阶段提前终止，正确结束与任务成功比一次 token/s 更重要。

一个 RTX 3080 10GB 用户在官方仓库讨论报告单槽设置前后总显存约 9.5 GB 和 7.8 GB（包括桌面占用）；厂商随后补充了相关说明。完整构建及两次分配日志仍不齐全，不可据此宣布所有设备能节省 1.7 GB。

在 Hacker News 原始讨论中，有开发者报告 24GB Mac mini M5 Pro 上 Q2 GGUF 的示例输出约 22.3 token/s，并报告一个小型公开 Bug 修复任务在独立测试条件下通过。这是第三方自行报告，未由本站复跑，也不代表同机器在 128K Agent 工作流或其他任务中的速度。

对独立开发者，更实用的指标应是每个有效任务耗时、错误调用数、恢复成功率、最终验证结果和峰值内存，而不是仅看生成速度。对于高精度量化仍有足够内存的设备，应在同一个 harness 下再比较质量和成本。不要将稀疏 MoE 与三值密集模型的激活参数和权重表示混为一谈，可参照另一类本地模型的部署选择。

6. 轻量化验证发现：官网 Demo 不一定就是新模型

2026-11-26 本站读取官网推荐 WebGPU 项目的原始 index.html，实际发现模型 ID 为 prism-ml/Ternary-Bonsai-2-27B-gguf，源码存在 WebGPU、本地模型加载路径，没有发现 2.5 版本标记。另一个厂商旧 Gradio Demo 的 app.py 仍引用更早的 Ternary-Bonsai-27B。两个公开仓库的 Hugging Face Inference Provider 映射均为空；针对 Bonsai 2.5 的 Space 搜索未返回匹配项，现有两个本地服务端口也未连接。

这些只是本次核验范围和时间点，不能证明全球不存在其他免费服务。它们足以阻止错误归因：不打开会下载权重的 WebGPU Demo，不以旧模型模拟新版、不购买 API、也不声称完成新版实际推理。源码入口来自官网与 WebGPU 项目。

本次 12 项独立检查包括五三值符号的穷举编码、组开销算术、GB/GiB 基本单位、三种真实文件顺序、三种 MTP 文件均较对应基础文件更大以及视觉文件分离。模型仓库 revision、API 文件字节数、源响应哈希、配置推导与结果均保存在实验目录。全部通过，不代表完成模型能力测评。

部署选型示意：标准 llama.cpp 需满足官方模型卡的 b11556 或更新版本要求；Apple Silicon 的 Metal 路径仍须匹配对应 GGUF 内核，MLX 使用独立模型资产。4K/8K 为后续测试起点，不是本站实际运行结果。

7. 本地 AI 的第二个价值：私有可控、数据安全与隐私边界

为什么要把 27B 模型压缩到可以在个人电脑或受控服务器上部署？除了降低硬件门槛，更重要的是为数据自主可控（AI data sovereignty）提供一种技术选择。用户可以决定模型版本、数据保存位置、访问权限和执行策略。但 Ternary Bonsai 2.5 27B 的压缩成果只涉及模型部署的可行性，不能证明采用该模型的应用已经安全、合规或完全离线。

本地 AI（Local AI）指在用户控制的设备或基础设施上执行推理；端侧 AI（on-device AI）更强调直接在终端执行；边缘 AI（edge AI）也可运行在靠近数据源的网关或边缘节点；自托管 AI 可以运行在自有服务器，私有化部署也可能采用隔离的云环境。离线大模型则要求运行所需权重、运行时、检索和工具都可在断网条件下使用。数据本地化（data residency）解决数据存放地的问题，数据自主可控还包括谁可以访问、何时传输、如何审计和删除。几个概念不能直接画等号。

本地 AI 与云端 AI：敏感数据在哪里流转？

部署方式数据边界典型取舍
端侧离线推理文档、向量和推理均在本机；仍要检查应用联网、备份和日志个人资料、离线任务；受设备内存和模型能力限制
自托管或企业私有 AI数据在受控服务器或私有网络中流转；需隔离租户、管理身份、加密和审计企业内部知识库、商业敏感文档；运维、硬件和合规成本由部署方承担
BYOK 混合模式本地检索后按授权发送必要证据片段；第三方提供商可能处理这些内容兼顾本地数据控制与云端模型能力；API Key 自有不代表数据仍在本机
云端 AI输入及相关上下文可能发送到远程服务，保留期限和使用范围取决于合同及配置弹性计算、复杂任务；需要核实隐私政策、传输和访问边界

上述为架构比较而非 Bonsai 2.5 的网络行为实测。对于本地 RAG 或私人 AI 知识库，一条可审计的参考链路是：本地导入与解析 → 本地 Embedding/索引 → 检索与重排 → 最小必要证据 → 本地推理 → 引用校验。云端生成和远程工具必须是单独授权的路径，而不是默认回退。即使模型在本地，远程 OCR、Embedding、Reranker、遥测、崩溃报告、云同步或 MCP 工具仍可能形成数据外传通道。详见本地 AI 与 BYOK 数据边界。

风险面建议控制与验收方式
模型供应链固定可信仓库 revision 与运行时版本；下载后重新计算完整文件 SHA-256 并与可信记录比对；审查依赖和模型加载代码，不因方便开启任意远程代码执行

AI Agent 安全专题和MCP 工具投毒风险进一步解释为什么本地 Agent 仍需对外部工具与检索内容设置独立权限。上述控制是部署建议和后续验收清单，不是本次已完成的安全测试，也不意味着该模型或 OwnRAG 已通过安全认证。

决策原则： 如果业务优先处理个人资料、企业内部文档或商业机密，隐私优先 AI 与私有化大模型部署值得评估；但不能用数据不出设备的承诺替代实际网络验证，也不能用更小权重代替任务准确率。对个人设备、私有服务器及云端混合模式分别记录硬件投入、运行能耗、维护、安全审计和人工复核成本，再按任务复杂度选择。本地模型不必完全替代云端模型。

参考架构示意，不是安全测试或认证。默认本地处理并不自动确保数据不外传；显式授权的云端模型及远程工具可能处理必要的输入，仍须验证权限、网络、日志和数据传输。

8. 如何决定是否用于私人知识库和本地 Agent

对 OwnRAG 一类本地知识库，模型负责生成不等于模型独自完成检索。优先分开测量 Embedding、检索、重排、证据拼接、生成和引用验证；参见端侧检索实验和本地知识同步架构。对 4GB 内存级手机，不能拿 5.58 GiB 文件推出全量常驻推理可行，也不能承诺某款 App 已适配该模型。桌面内存充足也不意味着质量已满足要求。

建议的下一轮最小验收：固定模型 revision、运行时构建及量化格式；首先用确定性结构化输出、短代码补丁、禁止越权调用、工具失败后恢复、证据不足拒答等合成任务；用独立断言评分，不使用模型自己的自评作为成功依据。逐渐增大上下文，记录错误与中止率、首 token 延迟、生成耗时、真实峰值内存。工具写入和联网默认关闭，真实任务执行由权限门禁控制，参见AI Agent 工具授权和本地 AI 与 BYOK 数据边界。

真正值得做的事情，不是让每一代大模型都在所有设备上跑一次，而是在设备约束、任务质量与资源成本之间获得可复现、可交付的决策。本文已完成模型资产预检，下一步只有找到可验证的新版免费推理入口或明确授权一次受控本地下载，才进行实际能力评测。

更多模型部署、端侧推理与隐私边界的工程研究，可从本地 AI 专题继续阅读。
