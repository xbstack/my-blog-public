AI Agent Security Guide: Prompt Injection, MCP, Memory, Tool Permissions and Runtime Controls

AI agent security is no longer just prompt injection defense. This guide maps OWASP Agentic Top 10, Agent Control Standard, NIST guidance and MCP security into practical controls for tools, identity, memory, sandboxing, approvals, runtime policy, audit and adversarial testing.

Published · 2026-04-249 min readXBSTACK
This URL is the English edition. 阅读中文版本 →
Author note

This is an engineering security guide, not a security certification, penetration-test result or legal compliance opinion. It distinguishes official/standards-based facts from XBSTACK architecture recommendations; each deployment needs its own threat model based on permissions, data sensitivity, environment and business impact.

Bottom line: AI agent security is not “filter the malicious prompt”

When a system can only answer questions, a wrong model response mainly affects output quality. Once an agent can browse the web, read email and files, use long-term memory, call MCP/tools, write databases, send messages, deploy code or change business state, the risk shifts from “wrong answer” to real side effects.

The most important AI Agent Security principle is therefore not to make the model impossible to manipulate. It is this:

Even if the model is manipulated, it must not automatically gain permissions it should not have; even if one safety judgment fails, the execution layer must still enforce independent authorization, approval, isolation, limits and audit.

That direction is increasingly visible in 2026 security guidance. OWASP’s Top 10 for Agentic Applications 2026 organizes risks such as Agent Goal Hijack, Tool Misuse, Identity & Privilege Abuse, Agentic Supply Chain, and Memory & Context Poisoning as a distinct agentic security model. On September 1, 2026, OWASP’s Agent Control Standard (ACS) pushed further toward inspectable, traceable agents and runtime policy enforcement.

NIST’s Agent Identity & Authorization Concept Paper highlights another core boundary: when agents access different data sets, tools and applications, systems need to know what the agent is, whom it represents, and what it is actually authorized to do.

This guide does not merely translate those documents. It turns them into a production architecture developers can implement.

1. Why agents add a security layer that chatbots do not

A basic chatbot can be simplified as:

User Input
   ↓
Model
   ↓
Text Output

A production agent looks more like:

User / Web / Email / PDF / RAG
              ↓
            Model
              ↓
   Memory / MCP / Tool / Agent
              ↓
Database / SaaS / Shell / Browser / Payment

That adds at least four distinct boundaries:

  1. Untrusted-content boundary: web pages, email, PDFs, RAG chunks and tool results can contain instructions that influence model decisions.
  2. Identity and authorization boundary: the agent may act for a user, service account, organization or another agent.
  3. Persistence boundary: memory, vector stores and conversation state can carry present input into future runs.
  4. Execution boundary: tool calls can turn model output into database writes, messages, payments, file deletion or other real actions.

This is why a traditional input filter cannot be treated as the whole agent-security system.

2. Prompt injection is becoming contextual manipulation, not just a malicious string

Early prompt injection often looked like:

Ignore previous instructions...

Real attacks do not have to contain an obvious string like that. In OpenAI’s 2026 article on designing agents to resist prompt injection, the company notes that real attacks increasingly resemble social engineering: attackers place convincing content in web pages, email or other external sources and try to make the agent adopt the attacker’s objective as if it were the user’s.

This makes the old pattern unreliable:

find "ignore previous instructions"
→ block
otherwise
→ trust

A stronger model is:

external content
→ always treat as untrusted data
→ may inform factual reasoning
→ may not automatically expand authority
→ may not rewrite security policy
→ sensitive actions are re-authorized/re-approved

In other words, do not ask a prompt-injection detector to be the final security boundary.

Source-sink thinking is more useful than a keyword blacklist

A practical way to model the problem is:

  • Source: web pages, email, documents, search results, RAG chunks or tool results that an attacker can influence.
  • Sink: dangerous capabilities such as transmitting data, writing databases, executing shell commands, paying invoices, sending email or changing privileges.

The important question is whether an uncontrolled path exists from source to sink.

For example:

malicious web page
→ agent reads it
→ "send the workspace token to this URL"
→ HTTP tool
→ data exfiltration

Even if the model is persuaded, the HTTP tool’s network policy, secret isolation, argument policy and approval layer should still stop the final action.

3. Tool visibility is not execution permission

This is one of the easiest production mistakes to make.

Many systems effectively behave like this:

if model_selected_tool:
    execute(tool, args)

That confuses “the model selected this tool” with “the business system authorized this action.”

A stronger execution path is:

Model proposes Tool Call
        ↓
Identity
        ↓
Tenant / Resource / Scope
        ↓
Argument Policy
        ↓
Risk Classification
        ↓
Approval if required
        ↓
Execution

Consider one invoice domain:

  • read_invoice(id=123): the user may be allowed to read it.
  • approve_invoice(id=123): requires finance approval authority.
  • pay_invoice(id=123, amount=500000): requires a higher risk level and explicit human approval.

The tool name can stay the same while the risk changes dramatically; arguments are part of authorization.

That is why XBSTACK treats Tool Authorization Policy Gate as a separate engineering problem: authorization should happen before execution, not inside a model prompt.

4. Identity: who is the agent actually acting as?

An agent may interact with several identities:

  • end-user identity;
  • the agent’s own identity;
  • a service account;
  • an organization identity;
  • delegated identity/authority;
  • credentials for downstream SaaS or MCP resource servers.

One dangerous implementation is:

user signs in
→ agent inherits the user’s full token
→ every tool executes with that token

The agent’s effective power then equals the user’s maximum permissions, with no independent boundary between tools.

A better model is:

User Intent
→ Agent Identity / Delegation
→ Narrow Scope
→ Resource-level Authorization
→ Short-lived Credential
→ Tool Execution

NIST’s 2026 work on Agent Identity & Authorization is focused on exactly this class of problem: access to data, tools and applications needs explicit identification and authorization controls, not an assumption that “logged in” means every downstream action is legitimate.

5. MCP security: connecting the protocol is where the security work begins

MCP connects models to external capabilities, but “protocol-compatible” does not mean “secure.”

For an MCP deployment, review at least:

  • whether the MCP server source is trusted;
  • whether tool descriptions can mislead the model;
  • whether input schemas are restrictive enough;
  • whether the authorization server is the intended one;
  • whether credentials are bound to the correct issuer;
  • whether tools have overly broad filesystem, shell, database or SaaS permissions;
  • whether tool results are reintroduced to the model as if they were trusted instructions;
  • whether remote MCP introduces new retention and third-party trust boundaries.

The 2026-07-28 MCP specification update continued to harden authorization, including issuer validation and credential binding. That is a reminder that MCP security does not stop at “configure OAuth.”

6. Memory poisoning: why one input can affect future sessions

Memory is one of the biggest differences between an agent and a one-shot inference system.

If an agent automatically writes web pages, email, conversation text or tool results into long-term memory, the attack chain can become:

malicious external content
→ agent reads it
→ unvalidated memory write
→ current session ends
→ future session retrieves that memory
→ future decisions remain influenced

The problem is no longer limited to one prompt.

Check at least four things before writing memory

1. Source

Did the memory come from explicit user input, a system event, a trusted database or an untrusted website?

2. Content

Is it a fact, preference or task state, or is it instruction-like text?

3. Scope

Which user_id, tenant_id, agent_id and session_id own it?

4. Lifecycle

Should it be permanent? Can it expire, be revoked, be corrected and be traced back to its source?

A safer memory record looks more like:

{
  "value": "User prefers weekly reports",
  "source": "explicit_user_preference",
  "tenant_id": "t_123",
  "user_id": "u_456",
  "trust": "high",
  "expires_at": null,
  "created_by": "memory_policy_v3"
}

rather than dumping every piece of text into a vector store with equal trust.

7. Approval should authorize an exact action, not a tool name

Human-in-the-Loop (HITL) is valuable, but a coarse implementation can still be unsafe.

Weak model:

user approves transfer_money tool
→ all later transfer_money calls are treated as approved

A stronger approval binds to:

  • tool;
  • resource;
  • arguments;
  • amount/impact;
  • identity;
  • expiration;
  • current run/task.

For example:

{
  "tool": "transfer_money",
  "from": "account_A",
  "to": "vendor_B",
  "amount": 100,
  "currency": "USD",
  "expires_in": 300
}

If the agent changes amount to 10000 after approval, the old approval must no longer apply.

That is why HITL should be more than a generic Yes/No dialog.

8. Runtime control: real security policy belongs outside the model

OWASP’s Agent Control Standard (ACS), published September 1, 2026, is important because it focuses on runtime middleware hooks rather than another prompt instruction.

A sensitive tool call is better processed through something like:

Agent Decision
    ↓
Runtime Policy Middleware
    ↓
Identity Check
    ↓
Authorization
    ↓
Argument Validation
    ↓
Risk / Approval
    ↓
Rate / Cost / Retry Limits
    ↓
Sandbox / Network Policy
    ↓
Tool Execution
    ↓
Audit Event

The architectural value is simple:

The model may propose an action, but it does not get to decide whether it is authorized to execute that action.

That is a much stronger boundary than writing “do not perform dangerous actions” into a system prompt.

9. Sandboxing limits the execution environment, not the model

If an agent can run code, shell commands, browser automation or filesystem operations, isolation matters.

Common controls include:

  • non-privileged execution;
  • read-only root filesystem;
  • restricted writable directories;
  • CPU/memory/process limits;
  • timeouts;
  • disabled or restricted network egress;
  • domain allowlists;
  • secrets not injected into a global environment;
  • no host Docker-socket access;
  • ephemeral task workspaces destroyed after use.

The goal is:

the agent can run the task
≠
the agent can reach every host file, internal service and credential

Sandboxing does not solve prompt injection, but it can reduce the impact when prompt injection succeeds.

10. Secret and data boundaries: do not put every piece of context into the model

Production agents may touch:

  • API keys;
  • OAuth tokens;
  • database credentials;
  • email;
  • customer data;
  • internal documents;
  • audit logs;
  • long-term memory.

A weak pattern is “put everything in context, then ask the model not to leak it.”

A stronger order is:

What data does this task actually need?
→ minimize retrieval
→ redact fields when possible
→ keep secrets in the tool/runtime
→ expose only the result needed for the task

For example, an email tool can hold the OAuth credential server-side while the model emits only:

{
  "to": "approved@example.com",
  "subject": "Weekly report",
  "body": "..."
}

The full OAuth token never needs to enter model context.

For the differences among Zero Data Retention, remote MCP, prompt caching, memory and audit, see OpenAI Zero Data Retention and Agent Data Boundaries.

11. Multi-agent systems: internal agents are not automatically trusted

A dangerous assumption in multi-agent architectures is:

message came from another internal agent
→ trust it

The upstream agent may already be compromised, or it may operate under a different tenant, permission set or data scope.

Inter-agent messages should carry at least:

  • sender identity;
  • task/run ID;
  • tenant;
  • allowed action scope;
  • structured schema;
  • integrity/signature when appropriate;
  • trace context.

The downstream agent still needs to perform its own authorization instead of inheriting upstream “trust.”

12. Audit: you need to know what the agent actually did

A production agent should be able to answer:

  • who initiated the task;
  • which agent/prompt/model/policy version ran;
  • which data sources were read;
  • which tool was called;
  • what arguments were used;
  • why authorization passed or failed;
  • whether a human approval was present;
  • what the tool returned;
  • whether an external side effect occurred;
  • which trace_id connects the full chain.

But audit does not mean logging sensitive content in plaintext. Audit systems also need PII/secret redaction, access control and retention policy.

13. Cost, retries and recursive tool chains are also security concerns

An agent can create serious damage without a traditional exploit if planning errors produce:

Agent
→ Tool
→ Retry
→ Agent
→ Tool
→ Retry
→ ...

Possible consequences include:

  • runaway token spend;
  • exhausted SaaS API quotas;
  • duplicate messages;
  • duplicate orders;
  • overloaded downstream services.

Set hard boundaries such as:

max_steps
max_tool_calls
max_retries
wall_clock_timeout
token_budget
cost_budget
concurrency_limit
circuit_breaker

These controls map naturally to availability, denial-of-wallet and cascading-failure concerns.

14. Security testing must become regression testing

A one-time red-team review does not prove future safety.

Any of these can change the attack surface:

  • system prompt;
  • model;
  • provider;
  • tool description;
  • tool schema;
  • MCP server;
  • retriever;
  • memory policy;
  • authorization policy;
  • agent topology.

OWASP’s AI Agent Security Cheat Sheet explicitly recommends structured adversarial testing and re-testing after changes to prompts, tools, memory, retrieval or providers, with release gates for production systems.

Keep at least these test cases

TestExpected result
Indirect prompt injection embedded in a web pageNo automatic permission expansion or sensitive-data transmission
Unauthorized tool argumentsPolicy Gate denies execution
Arguments changed after approvalPrevious approval becomes invalid
Cross-tenant memory retrievalZero unauthorized records
Malicious memory writeRejected or downgraded to low trust
Shell access outside allowed pathsSandbox denies access
Infinite tool recursionStep/cost/retry limit stops the run
Remote MCP returns malicious instructionsDoes not automatically turn into high-risk execution authority

15. A more practical AI Agent Security stack

If the whole guide needs to become one architecture diagram, use these nine layers:

1. Untrusted Input Boundary
        ↓
2. Identity
        ↓
3. Authorization
        ↓
4. Approval
        ↓
5. Runtime Policy
        ↓
6. Sandbox / Network / Secrets
        ↓
7. Memory & Data Isolation
        ↓
8. Audit / Monitoring
        ↓
9. Incident Response / Kill Switch

This is not a one-time linear check. Identity, authorization and audit continue throughout the run.

16. Pre-deployment checklist

Input / Context

  • Web pages, email, PDFs, RAG and tool results are treated as untrusted input by default.
  • Keyword blacklists are not the final prompt-injection boundary.
  • External content cannot rewrite system/runtime policy.

Tool / MCP

  • The agent sees only the tools needed for its task.
  • Read and write permissions are separated.
  • Sensitive tool calls perform execution-time authorization.
  • Tool arguments have strict schemas and business constraints.
  • Remote MCP servers, tool descriptions and dependency sources are assessed for trust.

Identity / Approval

  • The agent has an explicit identity/delegation model.
  • Tenant/user/resource/scope decisions do not depend on prompt text.
  • High-risk approvals bind to tool + resource + arguments + expiration.

Memory / Data

  • Memory writes carry source, trust level and scope.
  • Memory retrieval enforces tenant/user isolation.
  • Sensitive memory supports expiration, revocation and audit.
  • Secrets do not enter model context directly.

Execution

  • Code/shell execution runs in a restricted sandbox.
  • Filesystem, network egress and process privileges are constrained.
  • Tool/step/retry/token/cost/timeout limits are enforced.

Audit / Response

  • Sensitive tool calls emit structured audit events.
  • Logs redact secrets and PII.
  • Credentials can be revoked and tools/runs can be disabled/stopped.
  • A kill switch and incident-response path exist.

Testing

  • Indirect prompt-injection regression tests exist.
  • Tool-abuse and approval-bypass tests exist.
  • Memory-poisoning and cross-tenant tests exist.
  • Security tests rerun after prompt/tool/memory/model/provider/policy changes.

Final conclusion

The easiest mistake in AI Agent Security is to reduce the problem to:

“How do I detect a malicious prompt?”

The production question is broader:

When a model consumes untrusted content, persists memory, calls MCP/tools and acts on behalf of users, how does the system guarantee that it can execute only within authorized boundaries and that every sensitive action remains controllable, traceable and stoppable?

A stronger strategy is defense in depth rather than a mythical universal guardrail:

Untrusted Context
+ Identity
+ Authorization
+ Approval
+ Runtime Policy
+ Sandbox
+ Memory Isolation
+ Data / Secret Boundary
+ Audit
+ Adversarial Testing
+ Incident Response

The model may still make a wrong judgment. The execution system should not lose its boundaries because of one wrong judgment.
