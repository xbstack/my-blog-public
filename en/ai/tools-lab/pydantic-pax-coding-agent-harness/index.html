What Is Pydantic Pax? Comparing Codex, Claude Code and the Future of Agent Harnesses

On November 25, 2026, Pydantic introduced Pax and the public beta of its AI Harness. Pax is a terminal coding assistant built on a composable harness SDK, not a new foundation model. The release separates model choice, execution capabilities, workspace and interface, offering developers another approach alongside Codex and Claude Code.

By November 27, XBSTACK had inspected three pinned distributions, recomputed the published eight-model SWE81 results and completed an isolated installation, CLI startup check and 60 timed offline harness runs on an M1 Pro. The synthetic dependent tool-chain experiment found that Code Mode reduced elapsed time with substantial injected request delays but increased overhead without those delays. No hosted commercial model was called; the experiment does not establish superior coding performance. The important question raised by this release is whether different execution frameworks can deliver better outcomes, lower costs and verifiable security boundaries with the same model.

Pax is worth evaluating, but the evidence does not yet justify replacing Codex or Claude Code across an established workflow. The more consequential proposition is an execution SDK that applications can assemble independently of the terminal interface. This article uses public documentation and research available on November 27. It includes isolated installation, CLI startup and measured offline Harness behavior, but not an independently executed commercial-model benchmark.

If you are choosing an AI coding assistant, separate three questions: Pax is a multi-model terminal tool, not a new foundation model; open-source software does not make inference free; our M1 Pro measurements validate installation, CLI startup and a fixed synthetic tool chain, not superiority on real coding tasks. The sections below explain installation, selection, measured overhead and safety boundaries.

Related research: AI tooling and evaluation research.

1. What Pydantic released

Pydantic is well known for Python data validation. That heritage is relevant to agents because plausible model outputs still need to become valid application inputs, although it does not establish superior coding quality.

Pax is distributed as pydantic-ai-pax. The PyPI 0.75.0 release records a November 25 release date, MIT licensing and a Python 3.11 minimum. This is the pinned release reference for this article, not a claim that it is the latest version. Open-source licensing does not make model calls or hosted execution free. Four layers are worth separating:

LayerResponsibilityAdoption question
Pydantic AIAgent loop, models, tools and structured outputDo we need an agent inside an application?
Harness SDKReusable execution componentsWhich components fit the workflow?
CoderBundled coding capabilityCan we reuse an existing coding workflow?
PaxTerminal experience and pluginsShould this be our interactive entry point?

The Harness documentation and Coder reference explain how applications can reuse the components independently. The terminal is not a mandatory dependency of a custom coding agent.

This separation is useful, but interchangeable interfaces do not guarantee identical behavior. Changing a model or workspace can alter security, output handling and recovery.

Pydantic’s commercial position

It would be misleading to treat Pax as the auxiliary client of a foundation-model vendor. Pydantic’s company announcement established the open-source project as a foundation for the business. The subsequent Logfire launch and Series A announcement expanded that foundation into observability. Its current enterprise offering distinguishes the open-source framework from commercial support, observability and gateway services; the Gateway integration announcement documents the consolidation of one of those services.

The original validation library addressed a relatively deterministic problem: turning unchecked data into values an application could depend on. An agent adds a more difficult category of inputs. Its tool arguments, execution results and accumulated task state may have valid schemas while still describing an unauthorized or incorrect action. Validation is necessary but insufficient. A correctly typed deletion request can still address the wrong object, and a well-formed completion report can describe tests that never ran.

Pydantic’s plausible advantage is the ability to connect these concerns across the developer workflow, not an assumption that a validation-library maintainer automatically builds a superior coding agent. A terminal product exposes the behavior of the framework to users. The framework can become a point of integration for tracing, evaluation, model access and commercial assistance. That is an interpretation of the published product portfolio, not an assertion about private revenue or customer conversion.

There is a tension in this strategy. A freely available terminal can broaden developer adoption, but developers may use it without purchasing any service. Commercial integration can improve convenience, while excessive coupling would undermine the attraction of independent components. Useful signals are adoption of the SDK outside Pax, stable public interfaces, and whether commercial services offer measurable value without forcing a change of execution environment. Downloads or social-media mentions alone cannot answer those questions.

OpenAI’s Codex platform architecture already exposes its open harness through developer interfaces. Anthropic’s Agent SDK provides programmatic integration, approvals and tool controls. Pax is not the first extensible coding agent. Its distinction is making model choice and capability composition central.

A developer may prioritize familiar defaults and tight model integration. A team embedding agents may instead prioritize ownership of the work environment, authorization, task state and acceptance. These are different decisions, not necessarily competing products.

Seven products, different forms of control

Pax’s novelty becomes clearer when we expand the comparison beyond the native coding products. OpenCode agents document configurable agents and their permissions. The pi SDK offers a programmatic session abstraction. Deep Agents offers a reusable harness alongside its terminal coding product. DeepSeek Harness also emphasizes an extensible plugin architecture. None of these facts establishes a market-share ranking.

These are migration questions, not a list of established product defects. We did not run seven products in the same environment and do not assign subjective scores for usability or security. DeepSeek Harness is not a column in Pydantic’s published SWE81 matrix; missing benchmark data must not be interpreted as poor performance.

There is also a category distinction: a CLI competes for interactive work, while a library competes for architectural integration. Teams may retain Codex for daily repository work while using Pydantic AI or Deep Agents for a separate business application. They may also incorporate only one capability into an existing runtime. Forcing every candidate into a single replacement decision hides this flexibility.

The important competitive test for Pax is whether the modular architecture lowers the integration burden. If switching models requires redesigning every tool schema, approval policy, historical message representation and stopping rule, provider choice is only an adapter-level feature. Conversely, a single-model workflow that has stable task contracts and strong operational controls may be more economical. Technical openness and practical substitutability should be measured separately.

4. Model choice and migration do not eliminate lock-in

The Pax documentation describes importing Codex and Claude Code conversations using the corresponding resume options. Project instructions and skills also have supported discovery paths. Plugins can connect MCP tools and Logfire tracing or disable the coding capability. Select capabilities according to the task rather than enabling all of them.

There are three forms of portability: configuration, conversation history, and actual execution state. The third is the difficult one. A transcript can be reconstructed while its pending actions, approvals and external effects remain unresolved. Model-specific context behavior and native tools can also differ.

Before migrating, preserve the worktree and reconcile unfinished operations. For an agent that deploys software or updates a database, this is the unknown-outcome problem discussed in LangGraph failure recovery. A missing response does not prove that an operation never occurred.

5. Context, memory and model fallback are not one mechanism

GPT explanatory illustration; reconcile unknown external outcomes before retrying.

A common model interface addresses the beginning of a run. Long-running work also requires an understanding of what the system remembers and what it can verify. The separate documentation for Compaction, Tool Output Limits and Memory illustrates distinct concerns.

StatePurposeConsequence of losing it
Current contextEvidence and messages needed by the next requestIncorrect inference or repeated reading
Task progressVerified steps and unfinished requirementsRepeated or omitted work
Persistent knowledgeProject facts and relevant preferencesStale or untrusted information influences future runs
External truthFile versions, operation identities and business recordsDuplicate effects, incorrect rollback or false completion

Only the first category should depend entirely on prompt compaction. If a long tool result can be retrieved again, reducing it may be a sensible trade. Compressing a user’s authorization or a failed test into an ambiguous statement is different. A summary is not an independent record that a test passed or a transaction was committed.

Consider a coding task interrupted overnight. A migration script was written during the first session. In the morning, another developer changed the file. Resuming a conversation containing yesterday’s summary cannot establish today’s state. The restored agent needs the current worktree, a reliable baseline, an independent list of outstanding requirements and evidence of previous effects. The same holds when a conversation moves between clients. Successful transcript import is a much narrower outcome than successful workflow migration.

The Model Fallback capability addresses model-request failures and responses that cannot be accepted under the configured policy. It must not be confused with replaying a business action. If a provider fails while selecting a next step, a compatible fallback may continue inference. If a previous tool already initiated an external operation and its result is unknown, switching models is not permission to initiate it again. Organization safety rules and overall task budgets should carry across the fallback; model selection must not become a way to evade applicable restrictions.

Subagents add another boundary. Delegation can parallelize separable work, but each child must operate within a defined scope and report verifiable results. A parent’s job is to distinguish an ordinary child failure, user cancellation, an inference problem and an ambiguous external outcome. Concurrency without explicit ownership makes it harder to reconcile state. The evaluation should therefore test not only whether delegation produces a correct final answer, but also whether it duplicates work, consumes unexpected resources or fails to propagate cancellation.

The reported Sol cost reduction is approximately 56.2%, with a 4.6-point score difference. In the Opus comparison, the corresponding differences are approximately 2.0% and 0.8 points. The two configurations therefore do not support a universal claim that Pax halves coding costs.

The publisher identifies single runs, relaxed scoring for Sol and Opus, and max autonomy for Pax’s Sol configuration. Under the original grader, Sol scores are 51.0 and 49.8. That smaller difference shows why the scoring rule matters.

Among the four systems evaluated across all eight models, average scores span 57.3 to 58.5; Pax leads OpenCode by 0.3 points, while pi is cheaper on average. The figures are too limited to establish a stable overall ranking. The reported expenses are task-run averages, not subscription fees or complete project costs.

Independent research, Harness or Model?, reports same-model comparisons whose principal average contrasts were not statistically resolved. It is not a Pax replication. It is a useful warning against generalizing from a narrow benchmark.

The engineering metric that matters is cost per independently accepted task: total model, execution and human rework expenditure divided by the number of valid accepted tasks. If none pass, the metric is undefined. Correctness and authorization must both hold.

Our existing model versus harness guide addresses broader failure diagnosis. This article instead focuses on the specific decision to adopt Pax or its SDK.

How to build a credible coding-agent evaluation

The Harness-Bench project describes multiple realistic task families and task-specific evaluation. Pydantic’s current results are an illustrative matrix, not the complete repeat-run methodology. Without per-task outputs, we cannot construct honest confidence intervals or infer binary pass rates from aggregate scores.

The earlier Harness or Model? preprint provides a useful counterweight. Its two principal paired comparisons had intervals covering zero; the effect varied across repository and contest tasks. The authors themselves note the need to replicate a post-hoc partition. This is not an evaluation of Pax. It explains why a small overall lead should not be treated as a stable causal result for a new product.

A defensible organization-level test has two tracks. In track A, hold the model, repository, task, reasoning budget, access, time cap and evaluator as constant as feasible. This approximates a controlled harness comparison. In track B, allow each system to use its normal recommended configuration. This better represents the actual adoption experience. Declare the two tracks before running them; there is no need to force their rankings to agree.

Record the repository revision, exact model identity, tool version, environment digest, access restrictions, budget, output, changed files, termination reason and test results. Use repeated paired tasks and report uncertainty on paired differences. Keep unsuccessful attempts; never permit the agent under test to rewrite its own evaluator. A task can have a passing patch at the time limit, or a confident completion message without a passing patch. The two cases belong to different failure classes. Anthropic’s agent evaluation research offers a complementary distinction between execution traces and evaluated outcomes.

Rather than spending heavily to duplicate a vendor leaderboard immediately, this research produced a compact audit of three fixed wheel artifacts and the public data. Twelve checks passed: eight distribution and source-structure checks, three quantitative checks and one explicitly hypothetical cost illustration. These are not twelve successful runs of Pax.

8. Code mode and execution overhead

Tool-heavy agents can spend repeated model round trips on intermediate results that never needed to enter the conversation. Pydantic’s code mode uses Monty’s restricted Python environment to coordinate tool operations and return selected results. This may reduce coordination overhead.

A repository search and related file reads can be grouped into controlled inspection. Editing a file or initiating an external write changes the risk category. Interpreter restrictions do not secure a tool with excessive authority.

Measure model calls, input size, caching, execution time, tool results, acceptance outcomes and policy violations. A cheaper run is not necessarily more efficient if essential tests or approvals were skipped.

9. Workspace abstraction and execution boundaries

Pydantic’s workspace documentation describes a common interface for files and commands. It offers a way to change execution environments while keeping application tools conceptually similar. This separation reduces environment-specific integration work but does not, by itself, create isolation.

If a custom tool accesses the host directly instead of using the workspace contract, selecting a sandbox may not constrain that tool. Data synchronization is another issue: even an isolated environment can receive unnecessary files, local modifications or configurations. An adoption checklist should specify writable and read-only locations, allowed network access, the execution identity, which inputs are synchronized, and what happens when the workspace is discarded. Remote execution also needs a clear data retention and deletion policy.

Some of the remote providers described in the release route authenticated repository requests through a proxy rather than placing the corresponding authentication material inside the sandbox. This reduces one exposure path; it does not prove least privilege. The proxy’s authorization scope, auditability and revocation behavior still matter.

Streaming and speculation introduce an additional distinction. A static read may be safe to start ahead of the final tool request, while a state-changing action must wait for complete, validated arguments and authorization. Even a nominally read-only external query may disclose data, consume quota or observe a different state when run early. Reusing a result from before a file was modified can make later reasoning incorrect. Measuring seconds saved without examining stale reads, abandoned calls and rework would reward latency rather than reliable delivery.

10. Security and durability are separate questions

The default local Pax configuration does not introduce additional isolation or approval prompts. Open source does not establish safe operation. Pydantic’s permissions reference distinguishes matching command patterns from a real isolation boundary.

Likewise, the presence of configurable security features in Codex and Claude Code does not prove that every tool or configuration is protected.

Start with a disposable repository and restricted access. Treat plugins, repository instructions and MCP responses as untrusted inputs, not sources of permission. Require separate review before external effects. Related XBSTACK resources include MCP tool poisoning and agent security.

Pydantic also distinguished SDK durability from Pax’s current capabilities in its announcement. Saving conversation history does not establish crash-safe recovery. A reliable task system needs persistent operation identities, reconciliation of uncertain effects and appropriate renewed authorization.

Trusting data is not the same as authorizing actions

The v2.75.0 release notes document a compatibility change relevant to repository context, skills and memory: lower-authority workspace content should not automatically become higher-authority instructions. This is a concrete prompt-injection boundary.

An agent working on someone else’s repository may legitimately read project documentation, dependency descriptions and examples. Those materials can explain the task, but they cannot establish new authority over the host or external systems. Folder trust, permission to use tools and approval for a particular consequential action are three different decisions. Even if the model recognizes the provenance of a message, the application must independently enforce its tool policy.

The public security advisories provide a way to monitor affected versions and repairs. Their existence should not be used as a simple ranking of product safety, and a new release is not proof that every issue has been resolved. Open source makes inspection possible; operational safety requires evidence from the configuration in use.

ScenarioAppropriate controlRequired evidence

This is a proposed control matrix, not a statement that Pax passed these scenarios. It is especially important to keep the distinction when a product exposes both local and hosted environments.

The Pax user guide describes automatic loading of project environment configuration, repository trust and local session storage. Marking a folder untrusted does not by itself prevent file access or execution; it changes how repository material is presented to the model. Test in an empty disposable directory first, inspect the loaded components and data destinations, and verify organizational data-handling requirements before opening a production repository. Local execution does not mean inference data remains local.

The Coder documentation also separates autonomy guidance from enforced permissions. Asking the model to plan first is not a tool-level denial of writes, and requesting task completion is not blanket permission for external effects. An assessment must inspect actual accepted and rejected calls. Recheck authorization when a task is interrupted, resumed or delegated.

11. Conversation recovery, step persistence and durable execution

GPT explanatory illustration; factual and experimental claims are grounded in the article and underlying records.

The Step Persistence documentation describes recovery boundaries at stored steps, while Durable Execution covers execution engines. A stored conversation supports reconstructing context. A checkpoint can recover progress at a defined boundary. A durable engine may recover interrupted operations. None by itself proves that a remote service performed an action exactly once.

A useful business state machine is PLANNED, AUTHORIZED, DISPATCHED, CONFIRMED and ACCEPTED. When a connection fails after dispatch, record UNKNOWN and reconcile against the external system. A retry should occur only after the state and authorization justify it. This is independent of which model or interface continues the work.

For a software release, successful compilation, committed source, initiated deployment, public version verification and final acceptance are separate milestones. A timeout after deployment starts does not prove the public version stayed unchanged. On restart, the agent must inspect the actual release and its receipts rather than blindly repeat the entire process. The distinction is particularly relevant because the launch announcement excludes durable execution from Pax at that time, even while the SDK supports it for applications. Choosing a terminal client does not automatically produce a business execution platform.

12. How to evaluate Pax

The official documentation offers temporary execution through uvx and persistent installation through uv. Check the package version, provenance and command path first; macOS has an unrelated system utility with the same short name. Our subsequent pinned installation and CLI startup are documented in section 13.

Keep the established coding workflow while testing alternatives in isolation. Teams building Python-based agents may benefit from evaluating the SDK independently of the terminal.

Four initial task families can help:

Proposed testAcceptance criterion
Repository question answeringVerifiable references; no unwanted edits
Small bug fixCorrect patch; independent tests pass
Approval-sensitive actionNo unapproved external effect
Interrupted runConsistent state; no duplicate operation or false completion

Control repository revision, model, reasoning configuration, budget, authorization and environment. Repeat runs, retain failures and grade independently. Offline fixtures can demonstrate control behavior, not establish comparative coding intelligence.

These tests are proposals, not completed experiments.

XBSTACK runtime measurement: Code Mode on an M1 Pro

On November 27, 2026, XBSTACK used an Apple M1 Pro with ten CPU cores, 16 GiB unified memory, macOS 27.0.1 arm64, Python 3.11.15, Pax 0.75.0, Harness 0.75.0, Core 2.75.0 and Monty 1.7.0. The disposable environment accepted wheel dependencies only. The host sandbox denied home-directory reads and limited writes to the temporary directory; during runtime it denied networking, and a local socket bind was rejected. The temporary environment was removed. The Pax CLI help command returned exit code zero. This verifies startup, not an interactive coding session.

The timing test executed the installed Pydantic AI, CodeMode and Monty using the documented FunctionModel testing interface with provider requests disabled. Native mode emitted one predetermined tool call per scripted model request. Code Mode ran a loop in one run_code request, passing each increment result to the next step; a scripted completion response followed. Assertions verified the tool-call sequence, count and completion marker. Each configuration had one warm-up and five timed repetitions, for 12 configurations, 60 timed runs and 12 warm-ups. Fixed delays were artificially injected into each model response, not measured API latency or inference speed.

For context, Pydantic’s separate 5,276-run Code Mode study used eight actual models across five small applications and deterministic graders. It reported clear reductions in long-task cost and elapsed time, with overhead on some small tasks. Its earlier package versions, eager execution configuration and task set differ from ours; the benchmark code was not public, and it is not an independent Pax replication. The publisher also observed that real models can batch calls, suggesting that reduced context volume matters as well as round-trip count. Our fixture establishes a narrower mechanism: fewer scripted requests can reduce elapsed time for a prescribed dependent sequence with meaningful request wait. It does not establish the probability of generating a correct sequence.

There is also a migration cost not visible in the benchmark. A team must translate project instructions, plugin policy, conversation retention, provider configuration and organizational approvals. It must retrain developers and maintain integrations after API changes. On the other hand, a well-separated task contract can reduce future switching costs. Estimate the total cost of transition and of operating both systems during a pilot before counting theoretical savings.

14. Is the harness an AI operating system?

Calling the harness an operating system is an appealing analogy with important limits. An operating system offers relatively deterministic primitives for processes, memory, files and scheduling. An agent harness coordinates probabilistic model behavior with real execution. Similar coordination responsibilities do not imply kernel-level isolation, transactional guarantees or deterministic correctness.

A more precise analogy is a combination of application runtime and business middleware. The model proposes an action; the runtime provides execution and resources; the business system retains the authoritative record and policy. Middleware can remove duplicated engineering work, but an agent runtime must handle uncertainty about intent, changing model behavior and finite context.

One useful design separates three planes. The data plane carries model requests, tool results and application data. The control plane handles authorization, scheduling, budgets, tool selection and cancellation. The evidence plane records state changes, provenance, independent evaluation and rollback. A platform earns infrastructure status when these planes can be integrated and replaced without silently weakening their guarantees, not simply when it has the most extensions.

This direction is not exclusive to Pydantic. OpenAI’s harness engineering case emphasizes repositories that agents can inspect and independently validate. Anthropic’s long-running harness research emphasizes structured planning, generation and evaluation. Its Managed Agents architecture distinguishes sessions, harnesses and sandboxes. Native model vendors are investing in the same execution layer.

There are competing possibilities. As model interfaces become more interchangeable, open components may give adopters more choice. As models specialize in native tools and training-time environments, model-runtime coupling may instead become more valuable. The question is not answered by token prices alone. Measure the cost of preserving task semantics, authorization, state and acceptance when components change.

15. The future of agent harnesses

The launch offers evidence of an architectural direction, not a guaranteed market outcome.

First, model selection and execution tooling may become more separable. Better interoperability could encourage competition on accepted-task costs and reliability. Native platforms retain advantages in provider-specific features, infrastructure and product experience.

Second, reusable execution components may become more important to application frameworks. Workspaces, state management, authorization and observability could become replaceable infrastructure. Maintaining compatible abstractions across changing providers will also cost engineering effort. The announced 1.0 plan is not an achieved stability guarantee.

Third, applications may retain more control over authorization and acceptance instead of treating the model’s success statement as sufficient evidence. The valuable outcome is permitted, independently verified work.

In the next one to four weeks, watch API stability, permission behavior, complete benchmark methodology and independent reruns. Over six to twenty-four months, look for evidence that teams can migrate across models without losing state or authorization and sustain lower costs per accepted task. If interfaces remain unstable, safety controls are hard to deploy, or native platforms match the flexibility with stronger integration, Pax’s differentiation could diminish.

Over three to six months, look for actual delivery of the 1.0 compatibility policy, raw benchmark methodology and repeated trials, product-level durable execution, and improved permission defaults. Treat dates and feature announcements as hypotheses until releases and evidence exist. Over one to two years, measure integration effort, portable contracts, developer throughput, rework and costs on stable task suites. Further out, evidence and acceptance may become an important part of execution infrastructure. Yet native platforms may reproduce equivalent component interfaces while providing stronger integrated economics, limiting independent SDK differentiation.

Individuals do not need to predict the final market winner. Store the code, tests, requirements and task state in systems that remain under their control rather than binding all assets to a chat transcript. Teams can replace one layer at a time and evaluate the resulting behavior. Organizations should define approval responsibilities and verifiable completion independently of whichever model produces an answer. That is a useful architectural decision whether Pax eventually leads the market or remains a specialized alternative.

Conclusion

Pax is an interesting terminal coding agent and an example of a composable execution architecture. Early evidence supports competitiveness in specific configurations, not general superiority over Codex or Claude Code.

The better selection criterion is whether the system produces independently verifiable results within real operating boundaries. Preserve proven workflows and evaluate alternatives against actual tasks before switching.

Research cutoff: November 27, 2026. Forecasts are conditional engineering judgments. XBSTACK completed isolated Pax installation and CLI startup and measured the installed Harness with a scripted model; no paid model calls, penetration tests or independent vendor benchmark reruns were performed. This is architecture research with limited local runtime evidence, not a full coding-performance review.
