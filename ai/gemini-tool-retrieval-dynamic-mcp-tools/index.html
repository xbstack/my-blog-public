Gemini Tool Retrieval 实战：动态加载 MCP 工具，真的更省 Token、更安全吗？

Google 新推出 Gemini Tool Retrieval，使用 tool_search 和 defer_loading 延迟加载函数 Schema。XBSTACK 用 64 个合成工具对照静态、服务端与客户端检索，说明真实授权边界及适用条件。

当 Agent 接上几十个 MCP 工具时，为什么每次回答问题，都要把不相关工具的参数 Schema 一起送给模型？Google 2026 年 11 月 19 日推出的 Gemini Tool Retrieval（Preview），就是为解决这一类上下文膨胀问题：在 Interactions API 中使用 tool_search，为部分函数设置 defer_loading: true，等确实需要调用时才载入完整参数定义。

但答案有一个关键边界：它优化工具的发现与加载，不负责替应用决定用户有没有权限。 如果你的 MCP Server 包含「删除资料」「发送邮件」「退款」「查看私人知识库」，单纯开启延迟加载并不会令这些操作安全。Google 官方说明

这篇文章不做没有真实数据的“提速百分比”，而是对照官方协议与 XBSTACK 的一套 64 工具离线验证：区分三种检索方式、实际可见的 Schema 边界、业务授权、失败条件和后续真正需要测的 Token 成本。

一、三个问题先回答清楚

Gemini Tool Retrieval 怎么用？ 在支持的 Gemini Interactions API 模型请求中声明 tool_search，并将需要按需载入完整参数定义的函数标记 defer_loading: true。如果由应用自行检索工具，则把 tool_search 设置为 execution: "client"，再返回获得授权的完整工具定义。

它一定更省 Token 吗？ 不一定。Google 不对 Tool Retrieval 功能额外单独收费，但使用的输入/输出、载入的 Schema 仍按模型计费。工具库很小、常常全部使用，或者客户端检索引入额外往返时，整体收益可能很小。必须从实际 API 用量和完成任务总成本验证。

它会自动阻止 Agent 调用越权工具吗？ 不会。服务端延迟加载的工具名称和描述依然可能进入模型上下文；发现工具、选择工具与允许执行是三件不同的事。可信执行服务必须在真正访问外部系统前校验主体、资源、操作、参数和审批。

二、静态工具、服务端检索和客户端检索有什么不同？

模式工具怎样被发现模型最初获得的信息适用场景不应该忽略的限制
静态全量不搜索，全部工具直接声明所有名称、说明、完整参数 Schema工具很少、权限一致的助手上下文重复、工具列表可见性
服务端 tool_searchGemini 根据名称/描述寻找工具延迟工具的名称和描述；完整 Schema 按需加载体量较大、成员权限相同的工具库名称/说明仍可见；不做业务 ACL
客户端 tool_search应用的注册表或检索服务应用提供的搜索接口；按需返回获授权 Schema企业租户隔离、用户插件、动态 MCP 工具额外往返，权限和索引需要自行维护

根据 Google 发布的例子，服务端检索可以在一次请求的 interaction.steps 中留下 tool_search_call、tool_search_result 与 function_call；检索后的实际 Tool Executor 仍应由应用自己控制。客户端检索则通过 previous_interaction_id 将应用侧搜索得到的函数定义提交给后续请求。

这不是可以直接照搬到所有 generateContent 调用里的通用标记。 目前文档明确指向 Interactions API Preview，并声明 Gemini 3.6 与更新模型（含 Gemini 4）支持；实际应用必须核对模型、SDK 版本、地区及账户准入。Gemini API Changelog

服务端检索的官方字段形式

下面是依据官方示例整理的最小结构，不代表本站完成了真实 Gemini 在线调用：

from google import genai

client = genai.Client()  # 需要本人授权的 Gemini API Key
interaction = client.interactions.create(
    model="gemini-4-hydrogen",
    input="Find the report for project A-1042.",
    tools=[
        {"type": "tool_search"},
        {"type": "function", "name": "find_report",
         "description": "Find an authorized report by project ID.",
         "defer_loading": True,
         "parameters": {
             "type": "object",
             "properties": {"project_id": {"type": "string"}},
             "required": ["project_id"],
         }},
    ],
)
for step in interaction.steps:
    print(step.type)  # 观察执行步骤，不等于批准执行

Google 文档指出，服务端模式中的工具名称和描述仍会提供给模型，完整参数 Schema 才是延迟载入的部分；如果连某些工具是否存在都属于敏感信息，就不能把这类工具直接提交到同一个不加过滤的服务器检索集合。

三、64 个工具，本地究竟验证了什么？

XBSTACK 用 Python 标准库构造了 64 个合成 Function Schema，其中 3 个为当前用户允许的 read_docs、search_docs、export_document，其余包含未授权的 delete_document、issue_refund 等对照工具。脚本只产生确定性的 JSON 结构、运行本地权限过滤函数，没有联网、调用 Gemini API、MCP 远程服务或付费模型。

离线结构UTF-8 JSON 大小可推断的范围
64 个工具，完整参数 Schema 全部提供29,408 字节静态工具声明的合成大小
服务端延迟：64 个名称/说明加 tool_search9,911 字节这个结构的初始序列化长度较小
服务端结构再加一个实际需要的完整 Schema10,361 字节按需工具仍会被载入
客户端检索接口初始结构120 字节不包括后续检索轮次
客户端返回获授权、匹配的工具 Schema905 字节本地过滤返回的结构大小

四项自动化测试 4/4 通过。它们验证：用户只允许读/搜索工具时，客户端检索 delete 或 refund 不返回危险工具；服务端延迟工具列表却仍包含未授权工具的名称和描述。这正是工具注册表层过滤与真正执行授权相互独立的原因。

这些数值不是 Token 数、费用或模型延迟。 JSON UTF-8 字节无法直接换算为 Gemini 的 Token；这里没有测量缓存、工具选择准确率、额外回合、失败重试和账单。实验代码在项目 experiments/gemini-tool-retrieval-20261123/compare.py 及 test_compare.py，用 python3 -S 即可在本地复跑。

这张 GPT 生成的英文共用架构图是概念示意，不是 Gemini API 运行截图。三种工具发现方式最终都需要应用级 Policy Gate。

四、MCP 延迟加载，最大的坑并不是 Token

如果把一个 MCP Server 接入 Gemini，defer_loading 可能减少模型在开始时接收的完整工具参数。Google 官方文档也支持对远程 MCP Server 的工具延迟加载。但是：从外部 MCP 服务获得的工具描述，本质上是不可信输入。描述文字可能泄露权限信息，甚至夹带要求模型改变行为的指令。

例如，一个工具注册表允许用户「搜索自己的文档」，但同时注册了「删除全部知识库」。即使只声明后者的名称和简短描述，也属于把不必要的能力暴露给模型。更稳妥的方式是在返回工具列表之前按当前用户、租户、工作区和会话执行可见性过滤，然后在每次真实执行前重新验证。

对 OwnRAG 这样的本地 AI 私人知识库，有权使用工具与有权把资料发送到外部模型是两项独立授权。即使工具被发现，也不能自行把整库内容、未选中的证据片段或 API Key 送给远程服务。本文不声称 OwnRAG 已经集成 Tool Retrieval。

相关旧文：AI Agent 工具授权 Policy Gate 实战 讨论的是模型选择工具之后的主体、Scope、租户与参数授权；MCP Tool Poisoning 讨论恶意工具描述与外部依赖。本篇解决的是它们之前的工具发现与 Schema 暴露阶段，三个页面不应相互替代。

五、一个权限优先的动态工具架构

User request
  ↓
Authenticate user; obtain tenant, resource scope and permissions
  ↓
Filter registry before tool discovery
  ↓
Client tool_search returns only permitted full schemas
  ↓
Model selects a function (not an authorization grant)
  ↓
Backend checks identity, resource, arguments and policy version
  ↓
Require approval for consequential writes; stable operation key
  ↓
Execute or reject → log result → return minimum necessary data

即使有客户端搜索，执行前授权不能省。下面的伪代码只解释边界，不能替代生产身份系统和租户校验：

ALLOWED = {"read_docs", "search_docs", "export_document"}

def find_available_tools(registry, user_allowed, term):
    allowed = ALLOWED.intersection(user_allowed)
    return [tool for tool in registry
            if tool["name"] in allowed
            and term.lower() in tool["name"].lower()]

def authorize_execution(user_allowed, tool_name, resource_scope):
    if tool_name not in ALLOWED.intersection(user_allowed):
        raise PermissionError("Unauthorized tool")
    if not resource_scope:
        raise PermissionError("Missing resource scope")

实际执行还需要权限变更撤销、并发会话隔离、外部操作回执和幂等键。如果用户在对话中途撤销了 MCP 集成，下一次工具搜索必须更新可见性；此前已经生成、尚未执行的工具调用同样要被服务端拒绝。不要把 Tool Search 结果当作不会过期的访问令牌。

六、何时值得改造？先算通过验收的任务成本

Google Gemini API 价格文档说明常规模型输入输出按用量计费，官方同时指出 Tool Retrieval 不收单独功能费，但 tool_search 需要少量固定输入上下文，按需载入的 Schema 和模型输入输出仍计入对应的模型收费。客户端模式多一次应用端往返，可能增加整体延迟；延迟的 Schema 还可能让固定前缀缓存更稳定。以上是厂商描述，不是本站量化测评。

真正的性能实验应固定同一模型、同一工具集合和同一批任务，分别收集输入、输出、缓存 Token、被载入的工具数、检索次数、工具选错率、成功任务数、拒绝调用数、总费用与延迟。关键指标不是“初始 JSON 比原来少了多少字节”，而是一次完整任务通过验收总共耗费了多少资源。相关任务计费边界可参看 Gemini 4 Neon 的 Agent 成功任务成本分析，但两篇研究均不冒充 Tool Retrieval 真实 API 跑分。

如果只有五个工具，或者业务每轮都用到大部分工具，按需搜索未必更优。若有上百种工具、每轮只需要少数能力，并且工具已经经过授权过滤，那么 Tool Retrieval 才更值得逐步小范围引入。

七、上线前检查

  1. 确认 API 和 SDK 支持 Interactions Tool Retrieval Preview；不要把模型更新新闻当成完整兼容性保证。
  2. 先从注册表移除重复、弃用和无权访问的工具；特别检查名称/描述是否包含私人信息。
  3. 对敏感 MCP 工具优先使用客户端搜索与按用户 Scope 的工具可见性过滤。
  4. 对每次执行再检查主体、租户、资源、参数、审批与幂等，不相信模型自己做出的授权判断。
  5. 记录 tool_search、被选工具、最终 Tool Call、拒绝原因和任务验收状态；不要在日志保存不必要的私人资料。
  6. 只有收集真实 Gemini API 使用量、失败率和费用后，才能发布节约 Token 或提速结论。

结论：能动态找到工具，是能力；有权执行，才是产品责任

Gemini Tool Retrieval 把 Agent 工具库从“每次完整列出”推进到了“按需发现”，但它不是身份授权框架。工具少写进 Prompt 的同时，更要坚持工具注册表可见性过滤、执行前 Policy Gate 和可信审计。

XBSTACK 现在已经完成的是：官方接口研究、64 工具离线结构对照、4 项权限测试，以及真实实验需要哪些数据的验收方案。尚未完成的是 Gemini API 的静态/服务端/客户端三路线上测量，所以这里没有“降低 XX% Token”或“速度提升 XX%”等未经证明的数字。
